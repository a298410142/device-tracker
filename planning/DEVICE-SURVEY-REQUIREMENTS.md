## 1. 系統概述

### 1.1 背景與目標

DEVICE SURVEY 系統是一套「設備市場調查與採買決策輔助平台」，協助使用者：

- **掌握市場動態**：自動蒐集設備新品相關新聞，不需手動逐站瀏覽。
- **快速看出趨勢**：以熱詞文字雲視覺化新聞焦點，秒懂近期市場熱點。
- **做出採買決策**：彙整新聞趨勢、比價資料與規格，產出採買建議。
- **買在好價格**：串接 BigGo 比價 API，查詢即時售價與歷史價格走勢。

### 1.2 與既有系統的關係

本 repo 既有的「設備登記系統」（借用/歸還/歷史紀錄）負責設備的**使用生命週期**；
DEVICE SURVEY 負責設備的**採購前生命週期**（調查 → 評估 → 比價 → 採買建議）。

兩者建議整合為同一平台的兩大模組，形成完整鏈路：

```
[市場調查] → [採買建議] → [採購入庫] → [借用/歸還管理]
 DEVICE SURVEY                          既有設備登記系統
```

### 1.3 使用者角色

| 角色 | 說明 | 主要操作 |
|------|------|----------|
| 一般使用者 | 查閱資訊的同仁 | 瀏覽新聞、文字雲、比價結果 |
| 調查人員 | 負責市調的人員 | 設定關鍵字、排程、追蹤清單、產出採買建議 |
| 管理者 | 系統管理 | 帳號權限、API 金鑰、新聞來源、系統設定 |

> 若初期為個人/小團隊使用，可先不做權限分級，但資料模型預留 `role` 欄位。

## 2. 功能需求

### F1. 設備新品新聞蒐集（使用者指定功能 1）

#### F1.1 關鍵字搜尋
- 使用者可自行輸入關鍵字（例如「筆電 新品」「OLED 螢幕」「印表機 發表」），支援多關鍵字（AND / OR）。
- 可儲存常用關鍵字組合為「追蹤主題」，一鍵重查。
- 搜尋結果顯示：標題、來源媒體、發布時間、摘要、原文連結、縮圖（若有）。

#### F1.2 日期條件
- 可自訂查找日期區間（起日～迄日）。
- 提供快捷選項：今天 / 近 7 天 / 近 30 天 / 自訂。

#### F1.3 每日自動查找（排程）
- 每個「追蹤主題」可開啟每日自動查找，可設定執行時間（預設每日 08:00）。
- 自動查找結果寫入資料庫並標記為「未讀」，於儀表板顯示「今日新增 N 則」。
- 自動去除重複新聞（以 URL / 標題相似度去重）。
- （加值）查到新聞時可發送通知，見 F7。

#### F1.4 新聞來源
- 初期建議來源（擇一或並用，詳見 §4.2）：
  - Google News RSS（免費、無金鑰、支援中文與關鍵字查詢）
  - NewsAPI / GNews 等新聞 API（有免費額度，正式使用需付費方案）
  - 指定科技媒體 RSS（T客邦、iThome、TechNews 科技新報、ePrice 等）
- 管理者可在後台新增/停用新聞來源。

#### F1.5 新聞管理
- 收藏 / 標記重要新聞、加標籤（如「待評估」「已採買參考」）。
- 已讀 / 未讀狀態。
- 新聞列表可依日期、來源、關鍵字篩選與排序。

### F2. 新聞熱詞文字雲（使用者指定功能 2）

- 對指定範圍（關鍵字主題 × 日期區間）的新聞標題與摘要做中文斷詞，統計詞頻並繪製文字雲。
- 中文斷詞建議採用 `jieba`（前端可用 jieba-wasm / 後端用 nodejieba 或 Python jieba）。
- 支援**停用詞表**（過濾「報導」「表示」「公司」等無意義詞），管理者可自訂增刪。
- 字體大小依詞頻映射；滑鼠懸停顯示詞頻；**點擊熱詞可反查包含該詞的新聞列表**（鑽取分析）。
- 可切換時間區間比較（例如本週 vs 上週），觀察熱詞變化。
- 文字雲可下載為 PNG 圖檔（供放入報告）。
- 前端繪製建議使用 `d3-cloud` 或 `wordcloud2.js`。

### F3. 設備採買建議（使用者指定功能 3）

- 使用者建立「採買評估單」，輸入：設備類型、需求規格、預算範圍、數量、期望採購時間。
- 系統彙整以下資訊產出建議報告：
  1. **市場趨勢**：相關新聞數量趨勢、熱詞（來自 F1/F2）。
  2. **候選機型**：透過 BigGo 搜尋符合關鍵字的商品（來自 F4）。
  3. **價格分析**：各候選機型目前售價區間、歷史價格走勢、是否處於低點（來自 F4 價格歷史）。
  4. **建議結論**：依「預算內 + 價格處於歷史相對低點 + 近期無重大新品發表訊號」等規則給出「建議現在購買 / 建議再等 N 週 / 建議改選替代機型」。
- 建議報告可匯出 PDF / 列印（見 F8）。
- （加值，Phase 3）可串接 LLM（如 Claude API）自動摘要新聞重點並生成自然語言採買建議文字；純規則版本先行，LLM 為選配。

### F4. BigGo 比價 API 串接（使用者指定功能 4）

#### F4.1 BigGo API 現況（已初步查證）
- BigGo（[biggo.com.tw](https://biggo.com.tw)）為台灣比價平台，整合 momo、PChome、蝦皮等各大電商。
- BigGo 提供開發者 API（developer 平台 biggo.dev），主要能力：
  - **商品搜尋**（跨電商平台搜尋商品與售價）
  - **價格歷史**（指定商品的歷史價格走勢）
- 認證方式：於 BigGo 帳號設定產生 **Client ID / Client Secret**（OAuth2 client credentials 換取 access token）。
- BigGo 另有官方 [BigGo MCP Server](https://github.com/Funmula-Corp/BigGo-MCP-Server)，可作為 API 行為參考。
- ⚠️ **待確認**：API 申請流程、免費額度 / 計費方案、Rate limit、台灣站資料涵蓋範圍 —— 需註冊開發者帳號後確認，列為前置作業（§8 Phase 0）。

#### F4.2 功能需求
- **商品比價查詢**：輸入商品關鍵字 → 顯示各平台售價列表（平台、賣場名、價格、連結、商品圖），可依價格排序。
- **價格歷史圖表**：選定商品顯示歷史價格折線圖（建議用 recharts），標示歷史最低價。
- **追蹤清單與到價通知**：將商品加入追蹤清單，設定目標價；排程定期查價，低於目標價時通知（見 F7）。
- **與採買建議整合**：F3 評估單可直接引用比價結果。

#### F4.3 技術約束（重要）
- **Client Secret 絕不可放在前端**。所有 BigGo API 呼叫必須經由後端代理（proxy），由後端持有金鑰並處理 token 換發與快取。
- 對相同查詢做結果快取（建議 TTL 1～6 小時），節省 API 額度。
- 需處理 API 失敗降級：顯示快取資料 + 「資料更新於 X 小時前」。

### 以下為建議補充的功能（使用者未提及，建議納入規劃）

### F5. 設備資料庫與規格比較
- 建立內部「設備/機型資料庫」：品牌、型號、類型、規格、上市日期、官方頁連結。
- 多機型**規格對照表**（並排比較），輔助採買決策。
- 從新聞 / BigGo 搜尋結果可一鍵「加入設備資料庫」。

### F6. 儀表板（Dashboard，建議設為首頁）
- 今日新增新聞數、未讀新聞、本週熱詞 Top 10（迷你文字雲）。
- 追蹤商品的價格異動（漲/跌幅）、到價提醒。
- 進行中的採買評估單狀態。

### F7. 通知中心
- 站內通知（鈴鐺）：每日新聞蒐集完成、商品到價、價格大幅波動（如單日跌幅 > 10%）。
- 外部通知（Phase 2+，擇一先做）：Email、Slack/Discord Webhook、LINE Messaging API。
- 每位使用者可自訂通知開關與頻率（即時 / 每日摘要）。

### F8. 報告匯出
- 採買建議報告匯出 PDF（含文字雲圖、價格走勢圖、新聞清單）。
- 新聞清單 / 比價結果匯出 CSV / Excel。

### F9. 帳號與權限（若多人使用）
- 登入（初期可用簡單帳密或 Google OAuth）。
- 角色權限見 §1.3；個人化資料：追蹤主題、追蹤商品、通知設定。

### F10. 與既有設備登記系統整合（Phase 3+）
- 採買評估單核准後 → 建立「採購紀錄」→ 入庫成為可借用設備 → 接上既有借還流程。
- 既有系統資料由 LocalStorage 遷移至後端資料庫（順勢解決現有資料不可跨裝置的限制）。

## 3. 非功能需求

| 項目 | 需求 |
|------|------|
| 效能 | 新聞列表 / 比價查詢回應 < 2s（含快取）；文字雲 1000 篇新聞內 < 3s 完成繪製 |
| 安全 | API 金鑰僅存於後端環境變數；後端 API 需驗證；HTTPS |
| 可靠性 | 排程任務失敗自動重試（最多 3 次）並記錄 log；外部 API 失敗時降級顯示快取 |
| 資料保留 | 新聞保留 ≥ 1 年；價格歷史長期保留；可設定自動清理策略 |
| 國際化 | 介面繁體中文；新聞來源以台灣媒體為主，預留多語擴充 |
| 響應式 | 桌機優先（調查工作場景），兼容手機瀏覽（沿用 Tailwind） |

## 4. 系統架構建議

### 4.1 整體架構

⚠️ **關鍵架構決策**：目前專案是純前端（React + Vite + GitHub Pages 靜態部署）。但本系統有三件事**純前端做不到**：
1. 每日自動排程查新聞（網頁關掉就停了）
2. 隱藏 BigGo Client Secret
3. 跨裝置共用資料（LocalStorage 只在單一瀏覽器）

因此**必須新增後端**。建議方案（依維運成本由低到高）：

| 方案 | 組成 | 適合 |
|------|------|------|
| A. Serverless（建議起步） | 前端續用 GitHub Pages；後端用 Cloudflare Workers / Vercel Functions + Cron Triggers；DB 用 Cloudflare D1 / Supabase（免費額度足夠） | 個人～小團隊，幾乎零維運費 |
| B. 單體後端 | Node.js (Express/Fastify) + SQLite/PostgreSQL + node-cron，部署於公司內部主機或 VM | 內網環境、資料須留在公司內 |
| C. 過渡方案 | GitHub Actions cron 每日跑爬取腳本，結果存成 JSON commit 進 repo，前端直接讀 | 最快驗證，但不適合長期（無法做即時查詢與金鑰代理） |

```
┌─────────────┐   HTTPS    ┌──────────────────────────┐
│  前端 SPA    │ ────────► │  後端 API                 │
│  React+Vite  │           │  - /api/news（搜尋/列表）  │──► Google News RSS / NewsAPI
│  Tailwind    │           │  - /api/wordcloud（詞頻）  │
│  recharts    │           │  - /api/biggo/*（代理）    │──► BigGo API（持有金鑰）
│  d3-cloud    │           │  - /api/advice（採買建議） │
└─────────────┘           │  - Cron：每日新聞 / 查價    │
                           └──────────┬───────────────┘
                                      ▼
                              資料庫（D1 / Supabase / PostgreSQL）
```

### 4.2 外部服務選型

| 用途 | 首選 | 備選 | 備註 |
|------|------|------|------|
| 新聞搜尋 | Google News RSS | NewsAPI、GNews、自建 RSS 聚合 | RSS 免費無金鑰；API 類有額度限制需評估 |
| 比價 | BigGo API | BigGo MCP Server（參考實作） | 需申請 Client ID/Secret，額度待確認 |
| 中文斷詞 | nodejieba（後端） | jieba-wasm（前端） | 詞頻統計建議在後端做並快取 |
| 文字雲 | d3-cloud | wordcloud2.js | 前端渲染 |
| 圖表 | recharts | chart.js | 價格走勢、新聞量趨勢 |
| LLM 摘要（選配） | Claude API | — | Phase 3 |

### 4.3 資料模型草案

```
topics            追蹤主題（id, name, keywords[], schedule_enabled, schedule_time, created_by）
news_articles     新聞（id, topic_id, title, summary, url(unique), source, image_url,

```

## 8. 名詞定義

| 名詞 | 定義 |
|------|------|
| 追蹤主題 | 一組已儲存的關鍵字 + 排程設定，新聞蒐集的基本單位 |
| 評估單 | 一次採買決策的載體，彙整需求、候選機型、比價與結論 |
| 到價通知 | 追蹤商品價格低於使用者設定目標價時觸發的通知 |
| 鑽取 | 從彙總視圖（文字雲）點擊進入明細（新聞列表）的操作 |
